# Cloudflare deployment

ShellDex is built by Astro and deployed as static assets on Cloudflare Workers.

- Production URL: `https://shelldex.com`
- Worker: `shelldex-com`
- Build output: `dist/`
- Routing: the production custom domain is declared in `wrangler.jsonc`
- Package manager: the exact pnpm version in `package.json` (11.19.0)

## Refresh metrics through Agent Vault

On Dave's workstation, with the approved `shelldex-github-metrics` service:

```sh
pnpm run enrich:vault
pnpm run deploy:dry-run
pnpm run check:sitemap
pnpm run deploy
```

The vault refresh collects repository metadata and latest releases on Luna via
Agent Vault, then transfers only the public snapshot back to this checkout.
Credentials never enter the repository. It requires SSH access to `luna` and the
Agent Vault wrapper at `~/.agents/skills/agent-vault-cli/scripts/luna_vault_run.py`.
The service uses `GITHUB_PUBLIC_READ_TOKEN` with bearer authentication for
`api.github.com/repos/*`. No GitHub write permissions are needed.

All repository responses must succeed and validate before project data is
changed. A 404 for a latest release means no published release. A 404 for a repository
retains its last known metrics with an explicit unavailable flag and the original
metric timestamp. Rate limits, authorization failures, missing responses, and
other API errors stop the update. Incomplete batches
must not be published. Repository IDs are retained so a reused URL cannot silently
replace a tracked project. For redirects, verify and update the YAML repository
URL; do not broaden Vault rules to follow unrelated paths.

For an environment with an approved `GITHUB_TOKEN` already supplied:

```sh
pnpm run build:refresh  # refresh, then build for review
pnpm run deploy        # validate, test, build, check sitemap, publish
# Or, to refresh and publish in one step:
pnpm run deploy:refresh
```

Do not run a refresh without authenticated access: the full batch exceeds the
anonymous GitHub API hourly allowance. Agent access to credentials must use
Agent Vault rather than a local .env file or another credential store.

## Saved data and ordinary builds

```sh
pnpm run validate
pnpm run test
pnpm run build
pnpm run check:sitemap
pnpm run check:editorial
```

Ordinary builds make no GitHub requests. They use `github_data` in the tracked
`src/data/projects/*.yml` files for all star counts and rebuild
`src/data/generated/leaderboard.json` from those same snapshots. A clean checkout
does not need an ignored leaderboard or star cache to build.

`src/data/star-history.json` retains daily star snapshots for growth calculations.
The refresh also backfills daily star additions from GitHub's paginated
`stargazers/history` endpoint into `src/data/star-activity.json`, keyed by
repository ID. It omits the incomplete collection day. The directory charts
the last 30 completed days and each profile JSON includes the stored series
as `daily_star_additions`. GitHub counts creation dates for stars still present
at collection time. Keep both history files with the refreshed YAML files. Seven-day
growth is unavailable until a snapshot from the actual date seven days earlier
exists. A first refresh or repeated same-day refresh must not manufacture zero
growth. Old `.enrichment-history.json` and `.stars-cache.json` files are unused.

There is currently no scheduled refresh or automatic deployment on Git pushes.
New projects and editorial descriptions still require YAML edits. The displayed check date refers to the data collection, not the date the HTML
was rebuilt. Unavailable repositories show their older metric date separately.

Metric-based editorial copy is generated by `src/lib/editorial.ts` from the same
saved snapshots. The FAQ renders the same ranking, winner description, and
language answers in visible text and JSON-LD. Comparisons require two measured
growth values covering the same week; missing history is never treated as zero.
`pnpm run test` exercises changing winners, ties, unavailable repositories, and
missing growth. `pnpm run check:editorial` checks the built pages against the
saved data and verifies visible FAQ answers match their structured data. The
normal deploy command runs this check before publishing.

## Cloudflare authentication and verification

Wrangler uses its local OAuth login. If it has expired, the human runs:

```sh
pnpm exec wrangler login
```

A deploy updates `shelldex.com` and does not publish a `workers.dev` hostname.
`src/worker.js` negotiates Markdown mirrors for HTML routes when clients request
`Accept: text/markdown`; other assets are served directly. Cloudflare Web Analytics is managed in the dashboard. After publishing, check:

```sh
pnpm exec wrangler deployments list
bash scripts/test-agent-ready.sh
curl -fsS https://shelldex.com/api/projects.json
curl -fsS https://shelldex.com/api/leaderboard.json
```

Verify all 54 projects (or the current registry count) appear, enrichment dates
are current, and project/leaderboard counts agree. Record the prior version before
publishing. To roll back, run `pnpm exec wrangler rollback <version-id>`.

## Dependency setup

If dependencies are missing, use only `sfw pnpm install --frozen-lockfile` under
the workstation package policy. Stop on any Socket warning, unknown result, or
fetch failure. Dependency changes and package-manager upgrades require human
approval; routine refreshes and deploys do not require dependency updates.
